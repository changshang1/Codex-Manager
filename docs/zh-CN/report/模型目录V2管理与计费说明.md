# 模型目录 V2 管理与计费说明

本文说明 OpenAI 官方 Codex 目录、CodexManager 受管模型目录 V2、route、instructions
policy 和钱包计费的实际行为。两套目录按平台 Key 的轮转策略分流；旧模型来源、旧价格规则
和供应商模型发现表只为迁移审计保留，不再参与请求。

## 1. 模型目录分流

- 纯 `account_rotation` 的 `/v1/models` 使用 OpenAI 官方账号池目录。目录按平台 Key 和
  Codex client version 缓存；同步失败时可以保留上一份可用快照。
- 非分发模式的纯账号池请求不受本地 V2 的 enabled、visibility、instructions policy 或
  `account_pool/default` route 阻断。V2 中存在 enabled 账号 route 时可作为可选上游模型
  覆盖；不存在时原样转发客户端请求的官方模型。
- `aggregate_api_rotation` 和两种混合轮转使用 CodexManager 受管 V2 目录，并严格检查模型、
  平台 Key 权限、价格和 enabled route。
- 分发计费模式下，即使是纯账号池也继续执行严格 V2 校验，避免官方新增但尚无本地价格的
  模型形成未计费调用。
- 受管 V2 模型来源只有 `builtin` 和 `custom`。
- fresh DB 会写入 9 个 builtin：8 个 `visibility=list` 模型立即显示在普通列表中，`codex-auto-review` 为 `visibility=hide`，只能通过 hidden 筛选管理或按 slug 显式请求。
- 受管 `/v1/models` 只读取 enabled、`visibility=list`、`supportedInApi=true` 的 V2 数据，不向
  聚合供应商请求 `/models`，不补建记录，也不写数据库。
- 其他模型通过“新增自定义模型”手工添加，或从本地 JSON 导入。

`gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna` 已按 OpenAI 官方 API 价格分别写入 5/0.5/30、2.5/0.25/15、1/0.1/6 USD / 1M tokens 的 input/cached input/output 基础费率，状态标为 `official`。输入达到 272000 tokens 时，三款模型分别切换到 10/1/45、5/0.5/22.5、2/0.2/9 的长上下文费率；hidden 的 `codex-auto-review` 仍明确显示 `price missing`，不是零价。

`gpt-image-2`（快照 `gpt-image-2-2026-04-21`）是第 9 个 builtin 和第 8 个可见 builtin。其 capability 只声明文本/图片输入、图片输出、图片生成与编辑，以及 `/v1/images/generations`、`/v1/images/edits` 两个直接端点；不声明文本生成或透明背景支持，也不能把该 slug 直接当作 `/v1/responses` 或 `/v1/chat/completions` 的主模型。Responses 中由主模型调用 `image_generation` 内置工具属于另一条接口链路，不能据此放宽这个目录项的用途边界。

## 2. 模型管理页

列表同时展示：

- origin：`builtin` / `custom`
- enabled 与 visibility
- price status：`official` / `estimated` / `custom` / `missing`
- instructions mode：`passthrough` / `fallback` / `override`
- enabled route 数量或 `missing route`

统计卡片显示 total、enabled、builtin、custom、price missing 和 missing route。hidden 模型不会混入默认列表，选择 hidden 筛选后才会出现。

删除语义：

- builtin 只能禁用，记录、价格和审计信息不会被物理删除。
- custom 可以物理删除。
- 删除聚合 API 连接时，会删除引用该连接的 V2 routes；不会反写 legacy 模型表。

## 3. 一次原子保存

模型编辑器分为四区，点击一次“保存模型”只调用一次 V2 upsert RPC，并由一个数据库事务保存：

1. 基本信息和关键 capabilities。
2. input、cached input、output 三价，以及可选 long-context tier。
3. `account_pool` / `aggregate_api` routes；上游模型名手工填写。
4. instructions mode 和可选文本。

同一事务还会保存 permission group 关联。任一步校验或写入失败，整次保存回滚，不会出现“模型保存成功但价格或 route 保存失败”的半状态。

价格 UI 使用 USD / 1M tokens；提交时从十进制字符串无损转换为整数 micro-USD。最多支持 6 位有效小数，禁止负数、非数字、部分三价和超出 JavaScript 安全整数范围的值。

长上下文 tier 的 `minInputTokens` 是包含 cached tokens 的总 input token 阈值。系统选择不大于实际 input tokens 的最高档；当前 `gpt-5.4`、`gpt-5.5` 以及三款 GPT-5.6 模型都在 272000 tokens 切换到长上下文价格。

## 4. 路由与聚合 API

每条 V2 route 包含：

- `sourceKind`：`account_pool` 或 `aggregate_api`
- `sourceId`：账号池使用 `default`，聚合来源使用连接 ID
- `upstreamModel`
- `enabled`
- `priority`：数值越大，运行时优先级越高
- `weight`：同一来源类型、同一优先级内的平滑轮转权重，必须大于 0
- `sortOrder`：只控制管理页面顺序，数值越小越靠前

builtin 默认拥有 `account_pool/default` route，上游模型等于平台 slug。aggregate route 只能由用户在模型编辑器中明确保存。

非分发模式的纯账号池不要求存在 `account_pool/default` route；该 route 只在存在时提供可选
的上游模型覆盖和调度。聚合 API 与两种混合策略仍要求请求模型拥有与策略匹配的 enabled
route，不能借纯账号池的官方直通规则绕过 V2。

`sortOrder` 允许负数、`0` 和重复值。相同时依次按来源类型、来源名称和 route ID 稳定排序；新建 route 默认取当前最大顺序号 `+10`。旧数据库升级时，按升级前页面顺序为每个模型回填 `10、20、30...`。顺序号不会影响真实请求选路。

聚合 API 页面只管理连接、启停、密钥、余额和 route 连通性测试。测试会从引用该连接的 enabled V2 routes 中选择具体上游模型，不会发现、同步或导入供应商模型，也不会调用供应商 `/models`。

Gateway 收到平台 slug 后按以下顺序处理：

1. 读取 enabled V2 model，并检查 `supportedInApi`、权限组和计费条件。
2. 按平台 Key 的轮转策略决定先尝试账号池还是聚合 API；模型 route 的优先级和权重只在同一来源类型内部生效。
3. 在同一来源类型内按 `priority DESC` 硬分层；高优先级组全部失败后才进入下一组。
4. 同一优先级内使用按“平台 Key + 平台模型 + 来源类型 + 优先级”隔离的平滑加权轮转。权重决定长期首选比例；首选失败后仍会尝试同级其它 route，再进入低优先级。
5. 为每个候选从不可变客户端 body 独立生成请求体，并将当前 route 的 `upstreamModel` 写入该候选请求，避免不同 route 或 provider 互相污染。

账号池 route 与聚合 API route 分别调度，不跨来源比较 priority 或 weight。账号池有多条 route 时，当前 route 的账号候选全部失败后才尝试下一条 route；同一个聚合 API 连接也可以由多条不同 `upstreamModel` route 形成不同尝试。进程重启会重置平滑加权的内存状态，不改变数据库配置。

账号上游返回 `400` / `404` 时，只有错误内容明确表示 `model_not_found`、`unsupported_model`、`model_not_supported` 等“当前上游模型不可用”语义，才按 route 级失败继续其它账号或下一条账号 route。自定义上游的 route 级 not-found 也不会让同一账号因旧的账号级 cooldown 而跳过下一条模型 route。`429`、挑战、账号耗尽等仍属于账号级状态，已写入的 cooldown 会跨 route 保留，避免把线路错误与账号健康状态混为一谈。

全局 `ordered` / `balanced` 只控制一条账号池 route 内具体账号的顺序，不再控制模型 route 或聚合 API route。聚合 API 连接记录上的 `sort` 只用于管理页和选择列表显示，不参与真实请求顺序。

`gpt-image-2` 的目录 capability 与本地请求校验把客户端用途限制在 Images API 兼容入口，route 本身不承担端点隔离。Images 适配器可以在内部转换为 Responses 主模型加 `image_generation` 工具；但客户端的普通 Chat Completions 或直接 Responses 请求即使显式填写该 slug，也不应绕过端点校验进入文本生成链路。

## 5. Instructions policy

| mode | 行为 |
| --- | --- |
| `passthrough` | 客户端已有 instructions/system/developer 内容时原样保留；模型文本不参与请求。 |
| `fallback` | 任一客户端 instruction channel 非空时原样保留；全部为空时才使用模型文本。 |
| `override` | 使用非空模型文本替换顶层和连续 leading system/developer instructions。 |

builtin 默认是 `passthrough`，且 `instructions_text` 为空。seed 不携带官方人格 prompt。

非分发模式的纯账号池跳过本地 V2 instructions policy，保持官方模型请求原样；聚合 API、
两种混合轮转和分发计费模式继续应用上表规则。

真实 Codex target 最终仍执行 transport 级中性兜底：当最终 instructions 为 missing、null、空串或纯空白时，发送 `Follow the user's instructions.`。该文本不写入模型目录；非 Codex target 不接收此兜底。客户端非空内容保持原字符串，不 trim。

## 6. 本地 JSON 导入

“从本地 JSON 导入”支持：

- 模型目录 V2 导出结构。
- Codex catalog 的 `models` 结构。

流程固定为 preview 后 commit。preview 显示新增、更新、冲突、跳过、错误和忽略字段；冲突策略只有：

- `keep_existing`
- `replace_custom`

所有导入项都作为 custom 处理，不能覆盖 builtin。`base_instructions`、`instructions_template`、instructions variables 和未知 prompt 字段会被忽略；导入不联网。

## 7. Codex 官方缓存边界

桌面端和 Web 端都不会写入或下载 `~/.codex/models_cache.json`，也不提供“导出到本地 Codex
缓存”入口。纯账号池的模型列表由 OpenAI 官方目录负责；聚合 API 和混合策略的受管 catalog
仅在 CodexManager Gateway 内按平台 Key 返回。保存或删除受管模型不会覆盖 Codex 客户端的
官方缓存。

受管 catalog 仍保存 GPT-5.6 的推理等级和 Codex 运行元数据：Sol、Terra 包含 `low` 到
`ultra` 以及 `multi_agent_version=v2`；Luna 包含到 `max` 且为
`multi_agent_version=v1`。目录还可包含 `tool_mode`、`use_responses_lite`、
`max_context_window`、`comp_hash`、verbosity、apply patch、truncation 和 speed tier 等非提示词
字段，不输出 `model_messages`，也不会启用 `include_skills_usage_instructions`。

Max 与 Ultra 不是独立模型。Max 是所选模型的单代理最大推理强度；Ultra 由 Codex 客户端在 Max 推理强度之上主动编排子代理。兼容客户端如果直接向 Gateway 提交 `ultra`，请求日志分别保存 `client_reasoning_effort=ultra` 和最终 `reasoning_effort=max`，列表显示为 `ultra→max`。未修改的官方 Codex 会在到达 Gateway 前把 Ultra 的单次上游请求归一化为 Max，因此 Gateway 不能仅凭请求体可靠反推用户是否选择了 Ultra；`x-openai-subagent`、父线程和 turn metadata 仍会原样透传，但不会被错误推断为 Ultra。

## 8. 整数计费与快照

计费只使用 V2 DB 中实际命中的价格 tier：

```text
uncached_input = max(input_tokens - cached_input_tokens, 0)

numerator =
    uncached_input * input_rate
  + cached_input_tokens * cached_rate
  + output_tokens * output_rate

charged_cost_microusd =
  ceil(numerator * multiplier_millis / 1_000_000_000)
```

`gpt-image-2` 的官方 image token 标准价为每 1M input / cached input / output tokens 8 / 2 / 30 USD，模型目录以这组数值作为官方价格元数据。这一目录记录不表示当前 Images API 兼容请求已归因到 `gpt-image-2`，也不表示当前请求日志或钱包会按这组 image token 单价估算或扣费。

中间值使用 `i128`，倍率应用后只做一次最终向上取整。实际 usage 优先；缺 usage 或流式中断时使用确定性本地估算并标记 `estimated`，不会默认为 0。

价格读取、request charge snapshot、幂等 wallet ledger 和余额更新在一个 Core 事务中完成。快照保存实际 tier/rates、tokens、usage source、倍率、base cost 和 charged cost；请求 ID / request log ID 用作幂等键。后续修改价格不会改变历史快照和钱包流水。

`price_status=missing` 的模型可以在非钱包模式使用，也可以继续编辑和配置 route；它不能加入钱包扣费权限组。钱包请求会返回 `model_price_missing`，不会按零价放行，也不会 fallback 到编译期价格。

## 9. 迁移行为

首次 V2 cutover 会在维护态下排空在途 Gateway 流量和钱包写入，获取数据库旁跨进程锁，并使用 SQLite online backup 执行 preflight、单事务迁移和 smoke test。失败时在恢复流量前还原 backup。

legacy DB 的迁移规则：

- builtin fixture revision 5 新增 `gpt-image-2`。既有 revision 4 目录缺少该 slug 时只补建这个 builtin 及其默认账号池 route；若同名 slug 已由用户作为 custom 管理，则保留 custom，不强制改写为 builtin。
- seed slug 复用对应 builtin 行；用户编辑字段、禁用状态和已验证显式价格优先。
- `114_model_catalog_gpt56_prices` 只为仍是 `missing` 且从未编辑的三款 builtin GPT-5.6 补价；任何自定义或已编辑价格都不会被覆盖。
- `115_model_catalog_codex_metadata` 把当前 fixture 的非提示词 Codex 运行元数据补到未编辑 builtin；`user_edited=1` 的模型保持用户值。
- `121_model_catalog_gpt56_official_prices` 只把仍保留旧版估算来源、三价和单一基础 tier 的 GPT-5.6 builtin 升级为官方缓存折扣与长上下文费率；自定义价格保持原值，模型其他字段即使已编辑也不会阻止未改价格获得修正。
- `129_model_route_sort_order` 为旧 route 增加 `sort_order`，按原页面顺序分模型回填为 `10、20、30...`，不会把该值用于运行时选路。
- 旧 custom 与 `user_edited=1` 的非 seed 模型迁为 custom。
- 普通、未编辑 remote rows 不进入 V2。
- 重复执行 seed/migration 不覆盖用户编辑。
- legacy 表保留用于审计，但运行时不再读取或写入这些目录、来源、映射和价格规则。

## 10. 常见排查

### 模型不在普通列表

先确认平台 Key 的轮转策略。纯账号池读取 OpenAI 官方目录，本地 V2 的 enabled/visibility 不
控制该列表；聚合 API 与两种混合策略检查 V2 的 enabled、visibility 和 `supportedInApi`，
hidden 模型只在 hidden 筛选中出现。

### 模型显示 missing route

在模型编辑器的“路由”页签添加 enabled route，并确认 aggregate route 的 source ID 对应仍存在且 active 的聚合 API。

### 钱包请求返回 `model_price_missing`

补齐 input/cached/output 三价后保存，或不要把该模型加入钱包扣费权限组。不要把空价格填写为 0 来绕过校验。

### 聚合 API 连通性测试提示没有 route

先在模型目录 V2 中为该连接保存一条 enabled aggregate route。聚合 API 页面不会自动发现上游模型。

### Codex `/model` 没有立即更新

不要尝试导出或手工覆盖 `models_cache.json`。纯账号池等待官方目录刷新，必要时重新加载账号
profile 或重启会话；聚合 API 与混合策略确认平台 Key 使用受管目录，并重新请求 Gateway 的
`/v1/models`。本地 V2 保存不会改变纯账号池的官方目录。
